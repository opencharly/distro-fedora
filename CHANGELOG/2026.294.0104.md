# 2026.294.0104 — fix(skills): re-home the ten fedora skill bodies to the candy/fedora-skills carrier so they reach ai.opencharly.skill (sdk#434)

## Summary

The ten `fedora*` `skill:` nodes in this repo were owned by **images** (`owner: fedora`,
`owner: fedora-coder`, …). Two consequences, both measured:

1. **Their prose could never be read.** A `skill:` body is read from
   `<owner candy SourceDir>/.agents/skills/<name>/SKILL.md` (`sdk/deploykit/skills_collect.go`).
   A `candy:` node carrying `base:`/`from:` folds into the **image** set and has no source
   directory, so an image-owned node's body is unreachable.
2. **They were silently absent from `ai.opencharly.skill`.** `CollectSkills` keeps only nodes
   whose `owner:` is in the image's composed candy chain — an image is never in that chain.
   The ten skills were therefore invisible in every Fedora image's label, not merely unreadable.

This PR gives them a real home: **`candy/fedora-skills`**, a package candy that declares a
`candy:` node, owns all ten skill nodes, and is composed into every Fedora image that carries one
of those skills. The bodies move **byte-identically** — no body was re-typed.

### This creates a new candy, and the measurement that made that the only option

The operator ruling on `opencharly/sdk#434` (`OPERATOR RULING, EXTENDED`) lifted the earlier
"do not create a new candy" constraint for exactly this reason, and it was measured twice:

- **16 of 17 image-owned nodes in this programme have no local package candy at all, and five of
  these images compose zero candies** — so "re-home to a candy the image already composes" is
  impossible, not merely awkward. `box/fedora` composed **nothing** before this PR (see the
  before/after `--format candy` below).
- **The candies most images do compose are `@github` refs** whose `SourceDir` is a read-only
  cache in another repo, so `owner:` cannot name them while the body stays here.
- **`opencharly/distro-cachyos` already carries this pattern** — `candy/cachyos-app-skills`,
  `-os-skills`, `-selkies-skills` hold skill nodes in this repo's sibling. Its only defect was
  that those dirs declared **no `candy:` node**, so `candy: [cachyos-os-skills]` failed with
  `candy "..." not found`. This PR completes that precedent rather than inventing a scheme: the
  carrier declares a real `candy:` node, so it can be composed.

Rejected: ownership by a semantically wrong candy (`charly-marketplace` is the ref-closure candy
here, and says so in its own `description:`). It would turn the gate green while leaving the
skill on the wrong candy and the label leg unmet — green and wrong.

`projectSkill` takes the file's frontmatter description unconditionally, so a node description
is unreachable prose — the R2 duplication this programme blocks on.

### What changed, file by file

- **`candy/fedora-skills/charly.yml` (new, 123 lines)** — the carrier `candy:` node (description
  + a documentation-only `plan:` modelled on `layer-charly-internals-extra`, the org's existing
  skill-carrying candy) plus the ten skill nodes.
- **`charly.yml`** — the ten skill nodes leave the root manifest (113 lines deleted).
- **`candy/fedora-skills/.agents/skills/<name>/SKILL.md` (10 renames, 0 insertions, 0 deletions)**
  — `git mv` from `.agents/skills/<name>/SKILL.md`; the repo root `.agents/` tree is gone.
- **the ten owning boxes** — each composes `fedora-skills`.
- **`AGENTS.md` / `README.md`** — both stated "the one local candy (`candy/charly-marketplace`)",
  which this change falsifies. Corrected in the same commit (R1).

Because `fedora` composes the carrier and is the root of the RPM hierarchy, every Fedora-derived
image now inherits it. That is the accepted cost of the ruling: a rebuilt Fedora image carries all
ten skills, whether or not it "owns" one.
