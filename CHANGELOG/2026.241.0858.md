# 2026.241.0858 — fix: reference layer-supervisord in six boxes + advance the layer-direnv pin

## Summary

Two fixes that between them take `check-sway-browser-vnc-pod` from **2 failed checks + 6 warnings**
to **0 failed + 0 warnings**.

**1. Six boxes resolve init `supervisord` with no supervisord candy in scan range.**
`charly box validate` warned about each:

```
warning: box "check-pod" resolves init "supervisord", which depends on the "supervisord" candy,
but no candy of that name is in this project's scanned set — nothing was injected, so the image
will declare init "supervisord" with no supervisord binary and fail at start. Reference the candy
directly in the box's candy: list, or pull it in via a composed candy's require:.
```

The warning is correct and the consequence is real: those images get stamped with
`init: supervisord` and no supervisord binary, failing at `charly start` rather than at build —
the exact silent-until-runtime failure the warning exists to catch. `check-pod`'s own description
even says it covers *"kind:pod runtime (nc :18794 + supervisord)"*.

Sibling boxes here (`web`, `valkey-test`) already reference `layer-supervisord:v2026.240.0121`
directly; these six did not. Added the same ref to each — exactly the remedy the warning names.

**2. The `layer-direnv` pin advanced** to `v2026.241.0738`. That candy's shell-init checks
asserted `/etc/profile.d/charly-direnv-<shell>.sh`, but charly builds the filename from the
candy's *model* name — post-cutover the repo — so it emits `charly-layer-direnv-<shell>.sh`.
`layer-direnv#2` corrected the assertions; this picks that up.
