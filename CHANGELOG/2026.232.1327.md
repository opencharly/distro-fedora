# 2026.232.1327 — fix the auto-merge revalidation race + re-finalization loop

The auto-merge workflow (`.github/workflows/auto-merge.yml`) was live-proven on
the first fix (2026.232.1246) — every gate passed — but the live run then
exposed three more defects that the stub-gh harness could not see:

1. **The revalidation race.** The CHANGELOG-finalization push creates a NEW
   head, and the revalidation ran immediately after the push — before the
   validator had created its check-run on the new head. `wait_all_settled()`
   saw ZERO check-runs (indistinguishable from "all completed") and
   `verify_all_green()` saw empty → green, so the merge proceeded and failed
   branch protection with `GraphQL: Pull Request is not mergeable
   (mergePullRequest)`. (Observed live in run 32371493249: the log shows
   `revalidation: all status checks have completed` 0.7s after the push, then
   the merge failure.)
2. **The `action_required` validator run.** A finalization push made with
   `GITHUB_TOKEN` does not dispatch jobs — the validator run it triggers ends
   `action_required` with 0 jobs and no check-run. The auto-merge could not
   re-run it (no `actions: write` permission), so the new head could never get
   a green validator check-run.
3. **The re-finalization loop.** Re-running the auto-merge re-finalized the
   changelog to a NEW stamp each time (2026.232.1256 → 2026.232.1304), creating
   a new head each time, and the cycle repeated.

## The fix

- **`actions: write`** permission added so the auto-merge can re-run the
  validator via the API.
- **`wait_for_validator()`** replaces the immediate revalidation after a
  finalization push: it waits for the validator run to appear on the new head,
  re-runs it via the API if it ended `action_required`/`startup_failure`, then
  waits for the validator check-run to appear before revalidating — so the
  merge never races ahead of the validator's check-run creation.
- **Idempotent finalization.** If the head branch's history already contains a
  finalization commit (a previous auto-merge run on this PR), the changelog is
  already at a merge stamp — the rename is skipped and that stamp is reused
  for the tag, so the changelog filename/H1 and the release tag still agree and
  the re-finalization loop is broken.

## Change class

**ci/config** — a workflow file + its CHANGELOG entry. No code, no candies, no
beds. The R10 for a workflow change is the live run of the workflow itself,
which can only happen after this lands on `main`; the stub-gh proof above is
the pre-landing gate.
