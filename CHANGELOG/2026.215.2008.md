# 2026.215.2008 — tutorial-shell: the documented example becomes a real, tested box

opencharly.ai now teaches from a box that exists. `tutorial-shell` is quoted end to end by the
site's quickstart and concepts curriculum, and `check-tutorial-shell` keeps that quotation honest by
re-proving it on every acceptance run.

## What landed

| Entity | Where | What it is |
|---|---|---|
| `tutorial-shell` | `box/tutorial-shell/charly.yml` | a three-candy box on the bare Fedora base |
| `check-tutorial-shell` | `charly.yml` | its `disposable: true` pod bed |

## Why three candies, and these three

The box is a teaching artifact, so each candy earns its place by demonstrating one distinct idea a
newcomer has to learn, and nothing else is added:

- **`ripgrep`** — a pure TOOL layer: packages and probes, no service.
- **`sshd`** — a SERVICE layer, and the canonical init-polymorphism example (one `service:` list
  carrying both a `use_packaged:` systemd form and a custom `exec:` supervisord form).
- **`supervisord`** — the container init that actually runs the service.

A tools-only box would have been smaller, but it could not be deployed as a pod at all — nothing
would keep it up — so the deploy half of the lesson would have had no honest demonstration. Adding
a service candy was the alternative to adding a `sleep infinity` fixture, which would have taught a
pattern nobody should copy.

## The box asserts one thing, and only what composition produces

`tutorial-shell` carries a single `check:` step, `tutorial-shell-service-wired-into-init`: the
assembled `/etc/supervisord.conf` contains a `[program:sshd]` block.

That is the one claim no composed candy can make. `supervisord`'s own plan proves the init is
installed; `sshd`'s proves the daemon is installed; **neither proves sshd became a supervisord
program** — the wiring exists only because the two were composed. Drop either candy and the check
fails: regenerating without `sshd` emits no `supervisor/` fragment directory at all, so the block
cannot be assembled.

**Co-residence needs no check**, and an earlier draft of this box wrongly added three. Every
composed candy's plan runs against *this* image, so ripgrep's probes and sshd's probes both passing
already proves both landed. Restating them at box or bed level duplicates the candy (R3) — and the
duplicate passes for the wrong reason, since it is testing the candy rather than the composition.
The bed likewise carries no `plan:`. The rule is not "beds don't have plans" — `check-sway-browser-vnc-pod`
in this same file carries three, adding cdp/wl/record probes against a running desktop. A bed earns
its own steps when a claim needs a LIVE deployment *and* no composed candy already makes it. Here
every live claim is already covered by the composed candies' runtime probes, so a bed plan could
only duplicate them.

## Editing rule this creates

The site **excerpts** `box/tutorial-shell/charly.yml`; it does not paraphrase it. Editing the box is
therefore a documentation change too — re-read the pages that quote it and update them in the same
cutover. `/charly-distros:tutorial-shell` carries the rule.
