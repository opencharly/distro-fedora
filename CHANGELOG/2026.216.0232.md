# 2026.216.0232 — tutorial-shell drops the explicit init candy

`box/tutorial-shell` composes only `ripgrep` and `sshd`. The `supervisord` line is gone:
declaring a `service:` is what SELECTS an init system, so charly now adds that init's own
candy to the composition automatically and target-aware — `supervisord` for this container
image, nothing at all for a machine venue, which already has systemd. (The mechanism is
`deploykit.InjectInitDependsCandy`; see the `opencharly/sdk` leg.)

## Why this box

An earlier revision of this entry claimed this was the ONLY box exercising the injection live,
and that without this edit the fix would ship with nothing running it. **Both halves were false.**
**Six** boxes in this submodule resolve a `supervisord` that appears nowhere in their authored
base chain — `check-pod`, `composition-app`, `composition-source`, `selftest-image`,
`selftest-layer`, and this one. The other five are already in that state on `main`, and
`check-pod` alone backs six `disposable: true` pod beds (`check-pod`, `check-addcandy-pod`,
`check-stepkind-emit-pod`, `check-enc-pod`, `check-tunnel-pod`, `check-preempt-arbiter-pod`), so
this box is not the mechanism's only live consumer.

What this box actually contributes is not first coverage but *legible* coverage: it is the
teaching example quoted verbatim on opencharly.ai, small enough to read end to end, and the only
one where the injection is the point being demonstrated rather than an incidental detail. That is
a real reason to change it, and it does not need the false one.

This one enumeration was answered wrongly FOUR times, which is worth recording because each wrong
answer had a different cause and all four looked authoritative:

| Answer | Why it was wrong |
|---|---|
| "the only box" | written from memory, never measured |
| 5 | grepped the box file for `supervisord`, which counts PROSE — this box's own description names the init repeatedly |
| 7 | assumed box NAME equals DIRECTORY name; `k8s-box` lives at `box/k8s/`, so the sweep read a path that does not exist and scored the result as "never names it" |
| 6 ✓ | resolve each box name to its real file, parse the `candy:` sequence, and walk the authored `base:` chain — inheritance is not injection |

The 7 is the instructive one, and an earlier revision of this entry drew the wrong lesson from it.
It said a missing file and a file containing no match are "indistinguishable to `grep -c`". They
are not — `grep -c` reports the difference on all three channels:

| | stdout | exit | stderr |
|---|---|---|---|
| file present, no match | `0` | 1 | — |
| file missing | *empty* | **2** | `No such file or directory` |

The failure was one level up, in the shell that consumed it:

```sh
a=$(grep -c 'supervisord' box/$b/charly.yml 2>/dev/null || true); a=${a:-0}
#                                           ^^^^^^^^^^^   ^^^^^^^    ^^^^^^
#                                        discards stderr  discards   coerces
#                                                         exit 2     empty → 0
```

Three independent suppressions, each individually reasonable, together converting a loud error
into the specific wrong answer that looks like a finding. So the rule is not "distrust `grep -c`"
— it signals fine. It is: **a sweep whose NEGATIVE result is load-bearing must assert it read what
it thinks it read**, because `2>/dev/null`, `|| true`, and `${x:-0}` are exactly the idioms that
turn "I could not look" into "I looked and found nothing".

Before the sdk fix this composition built clean, validated clean, passed `charly check box`, and
then failed at deploy `[start]` with no supervisord in the image. It now reaches steady state:

```
charly check run check-tutorial-shell: PASS (steps=13)
```

Artifact proof: the emitted Containerfile resolves
`ARG BASE_IMAGE=ghcr.io/opencharly/fedora-supervisord:<tag>`, an auto-intermediate whose own
Containerfile runs `dnf install -y supervisor` — supervisord arrives purely by injection.

"Three candies" lived in two live surfaces in this submodule, and this entry originally named
one of them wrongly:

| Surface | Was | Now |
|---|---|---|
| `box/tutorial-shell/charly.yml:5` — the box `description:` | "Composes three candies on the bare Fedora base" | two candies, with the init explicitly absent because it is injected |
| `charly.yml:77` — the `check-tutorial-shell` bed `description:` | "three-candy box (supervisord + ripgrep + sshd)", listing "supervisord's control-socket check" as acceptance content | two candies, injection stated, and the control-socket probe explained as proof that an injected candy contributes its acceptance plan |

The `plan:` step comment was NOT one of them — it said "Drop either candy from the list above and
this check fails", which an earlier revision of this entry misattributed. It was still updated,
because "either" now has a different meaning once the composed list is two rather than three.

The bed description mattered most, and for a reason worth recording: it advertised supervisord's
control-socket check as acceptance content at a moment when that probe had stopped being
collected. The file defining the gate was claiming coverage the gate did not have. It is accurate
again only because `opencharly/sdk#120` restored the collection.

The box `description:` is baked into `ai.opencharly.description` and quoted verbatim on
opencharly.ai, so a stale line there is a published defect, not just a comment.
