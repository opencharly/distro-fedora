# 2026.232.0003 — fix the auto-merge release-tag field

The auto-merge workflow merged PRs but never minted the release tag: both the
already-closed and post-merge paths read the merge commit from
`.merge_commit.sha`, but GitHub's REST `GET /pulls/{n}` exposes it as the FLAT
`merge_commit_sha` string (`merge_commit` is `null` on the REST object). Every
merge therefore left the tag unminted — the post-merge poll never observed a
merge commit and died in its 10-minute timeout, and the already-closed path
silently skipped the tag. (Observed live: PR #20 merged at 15:25:35Z in run
32385963824, but `v2026.232.1524` was never created.)

The fix reads `merge_commit_sha` directly. The stub-gh harness's `/pulls/{id}`
mock now carries the real REST shape (`merge_commit_sha` flat, `merge_commit`
null), and all 17 decision paths / 63 assertions pass again.

This is the canary that live-proves the corrected workflow — a subsequent PR on
this repo must go green → auto-merge → tag before the byte-identical change is
propagated to the other opencharly repos.

## Change class

**ci/config** — a workflow file + its CHANGELOG entry. The R10 for a workflow
change is the live run of the workflow itself, which can only happen after this
lands on `main`.
