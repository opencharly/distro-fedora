# 2026.216.0007 — tutorial-shell drops the explicit init candy

`box/tutorial-shell` composes only `ripgrep` and `sshd`. The `supervisord` line is gone:
declaring a `service:` is what SELECTS an init system, so charly now adds that init's own
candy to the composition automatically and target-aware — `supervisord` for this container
image, nothing at all for a machine venue, which already has systemd. (The mechanism is
`deploykit.InjectInitDependsCandy`; see the `opencharly/sdk` leg.)

## Why this box, and why it is the coverage

This is the ONLY box in the tree that exercises the injection live — every other box still
names its init explicitly, so without this edit the fix would ship with nothing running it.
Before the fix this composition built clean, validated clean, passed `charly check box`, and
then failed at deploy `[start]` with no supervisord in the image. It now reaches steady state:

```
charly check run check-tutorial-shell: PASS (steps=13)
```

Artifact proof: the emitted Containerfile resolves
`ARG BASE_IMAGE=ghcr.io/opencharly/fedora-supervisord:<tag>`, an auto-intermediate whose own
Containerfile runs `dnf install -y supervisor` — supervisord arrives purely by injection.

## Prose kept honest

The box `description:` and the `plan:` step comment both said "three candies" and named
`supervisord` as one of them. Both now describe the two composed candies and state that the
init is deliberately absent because it arrives automatically. The description is baked into
`ai.opencharly.description` and quoted verbatim on opencharly.ai, so a stale line here is a
published defect, not just a comment.
