# 2026.232.0008 — make the release-tag mint actually mint (the 404-body existence guard)

The auto-merge run block's `ensure_tag` never mints a release tag. Observed live:
run 32397140298 merged PR #27 (merge commit `711a80ab`) and logged

    Merged at 711a80ab… — tagging v2026.232.1721
    Tag v2026.232.1721 already exists

yet `v2026.232.1721` was never created. The guard was

```bash
if [ -z "$(gh api "/repos/$REPO/git/refs/tags/$ver" -q '.ref' 2>/dev/null || true)" ]; then
  … mint …
else
  echo "Tag $ver already exists"
fi
```

`gh api` writes an HTTP 404's **response body to stdout** (`{"message":"Not
Found",…}`), and `-q '.ref'` is only applied to successful responses — so for a
tag that does NOT exist the captured string is the non-empty 404 body, the
`-z` guard is false, and the mint is silently skipped. The guard can never see
"absent": every mint attempt takes the already-exists branch.

**Why the stub harness passed.** The stub modeled the API's intended behavior
(`echo ""` when the tag is absent) instead of `gh`'s actual stdout behavior —
the exact stub-vs-live divergence that produced the live failure.

**The fix** checks existence against the **local git refs** — the checkout
fetches `+refs/tags/*:refs/tags/*`, so `git rev-parse -q --verify refs/tags/$ver`
is a real presence test — and the POST is the mint. A failed POST (a concurrent
run's 422 "Reference already exists") reads "already exists (concurrent mint)"
and never exits non-zero. Proven by the stub harness: new S19 (tag absent → mint
→ `Tagged` fires), S20 (POST fails → concurrent-mint message, exit 0), S4b (tag
present locally → skip) — 92 assertions / 20 scenarios, all passing.

The skipped tag for PR #27's merge (`v2026.232.1721` on `711a80ab`, matching the
finalized `CHANGELOG/2026.232.1721.md`) was backfilled add-only on the merged
HEAD after the merge.
