# 2026.320.1054 — feat(ollama): ship ollama v0.40.16 by advancing the box's two pins together

## Summary

The `ollama` box composes the ollama candy from `pod-ollama` and the CUDA backend from
`layer-ollama-cuda`; both refs still named v0.32.14-era tags. This change advances both,
which is what makes the box actually ship **ollama v0.40.16**.

This is the only composing box on the TARBALL path. On Arch and its derivatives `pacman`
owns the ollama version, so `OLLAMA_VERSION` selects the binary here and nowhere else —
which makes this box the one place the upstream bump has to land to take effect at all.

| ref | was | now |
|---|---|---|
| `pod-ollama` | `v2026.274.0620` | `v2026.320.1029` (the v0.40.16 candy, opencharly/pod-ollama#8) |
| `layer-ollama-cuda` | `v2026.274.0847` | `v2026.320.1042` (its `require:` attaching to that candy, opencharly/layer-ollama-cuda#7) |

**Both refs move in one change because the loader refuses the alternative.** Advancing
only one, measured on this tree:

```
$ charly box validate
charly: error: command "validate": validation error: candy
github.com/opencharly/pod-ollama resolved to multiple git tags with differing content
within one scope (box=ollama); using newest referenced v2026.320.1029
(from github.com/opencharly/pod-ollama@v2026.320.1029)
```

So the three pins are one cutover in producer-first order: candy → backend layer → this
box. The first two have landed and are tagged; this is the consumer leg that closes it.

## Change classification

**Breaking change + rollback:** none for consumers of this image beyond the image itself
reporting the newer upstream release (`ollama --version` → 0.40.16 instead of 0.32.14).
Rollback is reverting this commit, which returns the box to the v0.32.14 candy; the two
producer tags stay valid either way, because they are separate repos. A rollback must
move BOTH refs — reverting one alone reproduces the multi-tag error pasted above.

Change class: **Box config** — static `charly box validate`, live `check-ollama-pod` + its
fresh-rebuild re-verification.
