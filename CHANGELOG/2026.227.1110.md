# 2026.227.1110 — reconcile every candy pin to charly v2026.227.0914 (RPM Fusion OpenPGP verification reaches consumers)

`charly box reconcile --remote` brings all **158**
`@github.com/opencharly/charly/candy/*` pins in this repo onto ONE tag,
`v2026.227.0914`, across 38 files — the repo was at **two** versions (157 at
`v2026.201.0706`, plus `check-fedora-vm`'s `add_candy` charly at
`v2026.226.1719`), and the tool reports exactly that:
`github.com/opencharly/charly -> v2026.227.0914 (was at 2 versions)`.
`charly box reconcile` (no `--remote`) then reports `already reconciled — every
repo's pins are at one version`. The motive is a supply-chain fix this repo could
not otherwise reach. A blocking defect surfaced while proving it and is fixed
here too: nine host-side check steps invoked a bare `charly` instead of
`${CHARLY_BIN}`.

Note for whoever repeats this: `--remote` is idempotent only against a *fixed*
remote. It re-resolves the newest tag on every invocation, so re-running it after
a sibling repo publishes a newer tag silently re-bumps every pin — it did exactly
that here mid-cutover, moving all 158 pins to a `v2026.227.1026` that none of
this change's evidence covers. The pins were returned to `v2026.227.0914`, the
tag every proof below was produced against. Use the plain form to *check*
convergence; reserve `--remote` for a deliberate bump.

## Why this is not a routine pin bump

`candy/rpmfusion` installed `rpmfusion-free-release` and
`rpmfusion-nonfree-release` from URLs. dnf treats a URL argument as the
`@commandline` repo and, at default settings, installs it **without an OpenPGP
check** — it printed `skipped OpenPGP checks for 2 packages` and carried on. Both
release packages therefore entered every Fedora-derived image unverified.

The candy at version `2026.227.0830` fixes it: it installs Fedora's own signed
`distribution-gpg-keys`, imports the two RPM Fusion keys from it with `rpmkeys
--import`, and only then installs the release packages under
`--setopt=localpkg_gpgcheck=1`.

The main repo got that fix immediately, because a local candy directory
**shadows** the remote one. This repo has no local candies — every candy is an
`@github` ref — so it kept fetching the pre-fix `2026.144.1443` rpmfusion at the
old pin. Anyone resolving `opencharly/distro-fedora` as its own project root was
still installing both packages unverified. That is what this reconcile closes.

## What the 26 days actually change

Of the **83** candies this repo references, 62 differ between the two tags, but
only **9** differ in anything other than regenerated `skill:`/`marketplace:`
prose (which is inert for an image build — it never reaches a Containerfile or an
OCI label):

- **`rpmfusion` (2026.144.1443 → 2026.227.0830)** — the OpenPGP fix above, plus a
  new `rpmfusion-key-imported` check step asserting the key is in the rpm
  database. This is the only change with a security consequence.
- **`nodejs` (2026.159.1324 → 2026.226.1600)** — the Debian/Ubuntu NodeSource repo
  moves from node 20.x to 22.x, and a new check enforces a **node ≥ 22.19.0**
  floor. Fedora is unaffected in substance (its distro `nodejs` is already 22.x)
  but the new floor check now runs in every Fedora consumer too. `pnpm --version`
  gains an explicit `HOME` so it no longer depends on an inherited environment.
- **`google-cloud-npm`** — stops installing `@google/gemini-cli` itself and
  instead declares `require: gemini`. Every box here that composes
  `google-cloud-npm` (`fedora-coder`) already composes `gemini`, so the CLI is
  still installed — now at the `gemini` candy's pinned version rather than an
  unpinned `*` that could overwrite it.
- **`charly`** — the candy-body `localpkg:` map is replaced by a `packaging:`
  metadata section (the nFPM cutover) and the binary is installed by a
  `copy: bin/charly` run step. This repo's `check-fedora-vm` bed was already
  rewritten for that mechanism in 2026.225.1508; the pin bump is what finally
  makes the bed's assumption and the fetched candy agree.
- **`check-stack-layer` (2026.174.0100 → 2026.209.1500)** — adds a
  `check-expect-non-zero` step covering `expect_non_zero`.
- **`charly-mcp`** — the MCP tool assertion moves from `box.build` to
  `box.list.boxes` and gains a `timeout: 90s`.
- **`k8s-layer`, `examplestep-consumer`, `check-cross-local-driver-layer`** —
  prose only (`k8s: raw` → `kube: raw`, `emitPluginFragment` →
  `invokeVerbBuildEmit`, `charly bundle add` → `charly fleet add`).

## Proof the fix reaches consumers

Built from this repo as its **own project root** (no superproject, no local-candy
shadowing), with the identical probe baked into both images:

| image | `rpmfusion` candy | `RPMFUSION-KEY-COUNT` | verdict |
|---|---|---|---|
| `fedora-nonfree:2026.227.0945` | `2026.144.1443` (pre-fix) | **0** | FAIL |
| `fedora-nonfree:2026.227.0942` | `2026.227.0830` (post-fix) | **2** | PASS |

The post-fix build log contains **zero** `skipped OpenPGP` lines and zero
warnings, and the image's baked plan now carries `rpmfusion-key-imported`, which
passes against the rpm database rather than against a key file on disk. The
pre-fix image has no such step at all — its six rpmfusion checks all pass while
the packages went in unverified, which is precisely why the new step was added.

`box/fedora-nonfree/charly.yml` is byte-identical across the bases involved, so
the comparison is a clean single-variable test: only the `rpmfusion` pin moved.
The final tree reproduces the post-fix state as
`fedora-nonfree:2026.227.1032` (rpmfusion `2026.227.0830`, build exit 0, zero
`skipped OpenPGP`, zero warnings, `charly check box` 6 passed / 0 failed).

## The `${CHARLY_BIN}` fix (R9) — nine host-side steps probed the wrong binary

`check-pod` failed its `status-shows-pod` step. The step is `in_container: false`
— a **host** command — and it named the binary bare, so the shell resolved it
through `PATH` to whatever `charly` happens to be installed
(`~/.local/bin/charly`, `2026.223.1347`) rather than the binary under test. That
installed binary is older than this repo's schema stamp, so it tripped the
load-time gate — `config schema 2026.225.1508 is newer than this charly supports
(max 2026.223.1018)` — which surfaced as an opaque
`fetch resolved-project envelope` warning from the kubernetes status collector.

The bug is R9: a bed that does not drive the dispatching binary is not proving
the thing it claims to prove. Main already solved this — it uses `${CHARLY_BIN}`
(stamped by `sdk/kit/checkvars_charlybin.go` from `os.Executable()` of the
dispatching binary, explicitly never synthesized from `PATH`) at **47** sites and
has **zero** bare invocations. This repo was relocated out of main and missed the
sweep, keeping **9**.

All nine `in_container: false` sites now use `${CHARLY_BIN}` (R3 — the whole
sibling set, not just the one that failed): `status-shows-pod`, the two
`charly config status` steps (`check-enc-pod`, `check-enc-port-pod`), the four
`charly preempt status` steps, and `charly vm gpu plan vfio`. Upgrading the
installed binary was rejected as the fix: it would hide the R9 hole and it would
reopen at the next schema bump.

## Disclosed: three beds cannot run, all blocked upstream of this repo

Every one of them is blocked by the main repo's in-flight nFPM cutover, and no
edit here can reach any of them.

- **`check-fedora-coder-pod`, `check-charly-fedora-pod`** fail at `image-build`.
  `charly check run` exports `CHARLY_REPO_OVERRIDE` to the **local** superproject
  checkout, so the `charly` candy resolves to the in-development tree regardless
  of the pin; that candy's disposable-bed path builds its package via `charly
  generate-packages`, a command the current binary does not provide (`unexpected
  argument generate-packages`, exit 80). Verified independent of this change:
  with the reconcile stashed and the pin back at `v2026.201.0706`, the same bed
  fails at the same step with a byte-identical error.
- **`check-fedora-vm`** fails later, at `deploy-add`: the production localpkg leg
  tries to fetch the released package — `downloading published charly package
  (rpm) for candy charly` → `curl: (22) … 404`. The package is not published at
  that URL yet. This is not a consequence of the bump: `main` already pinned this
  bed's `add_candy` charly at `v2026.226.1719`, itself post-nFPM, so the download
  leg was already the active path before this change moved it to
  `v2026.227.0914`.

The `CHARLY_REPO_OVERRIDE` behaviour has a second consequence worth recording: a
bed's image build never consumes the `@github` pins at all, so a green bed would
not by itself prove anything about a pin bump. That is why the security proof
above deliberately uses `charly box build` + `charly check box`, which do consume
them.
