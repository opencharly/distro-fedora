# 2026.274.2213 — docs(beds): check-tutorial-shell description matches the three-candy box

## Summary

`box/tutorial-shell/charly.yml` composes three candies: `layer-supervisord`, `layer-ripgrep` and `pod-sshd`. It lists the supervisord init candy **explicitly**. The box's own comments state why: declaring a service selects an init, and "if the acting init's candy is not in the scanned set charly warns and injects nothing".

Two places in this repo still taught the older story, where supervisord was auto-injected and the box had two candies:

1. **The `check-tutorial-shell` bed `description:`**
   - Old wording: "two-candy box", "composes NO init", "PLUS the injected init's own probes … the proof that an injected candy still contributes its acceptance plan", "a block **neither** composed candy produces".
   - New wording: three composed candies, each contributing its own runtime probes, and "a block **no** composed candy produces on its own".
2. **The `tutorial-shell` skill** (`tutorial-shell-skill`)
   - Old wording: its description said "with the container init injected"; the properties table said "Init: supervisord — **auto-injected**, not composed" and "Candies: ripgrep, sshd"; it said "kept to two"; and it argued that "composing the init by hand is neither required nor correct … two candies rather than three".
   - New wording: supervisord is composed explicitly; the table, the "why these candies" table (which gains a `supervisord` row) and the explanation all match the box.

The maintainer commands in the skill (`charly -C box/fedora …`) are unchanged on purpose. `-C` builds the local checkout being edited, which is what that skill's reader needs.
